# 车机 IPTV 直播源（Android 4.2.2 车机专用）

给 **Android 4.2.2 车机（32 位 ARM）** 用的直播源清单。配合 **Perfect Player 1.5.3** 使用。

> ⚠️ 车机装 Perfect Player 请用 **1.5.3**，不要用 1.6.0.1。
> 1.6.0.1 只带 `arm64-v8a` 原生库，32 位车机装了也播不了（一播放就崩）。
> 1.5.3 含 `armeabi-v7a` / `armeabi`，才是 32 位车机该用的版本。

---

## 二、远程订阅（自动更新，不用手动换文件）

车机 `设置 → 通用 → 播放列表` 里填 URL：

```
https://gh-proxy.com/https://raw.githubusercontent.com/tommy4x/iptvlist/main/car-tv.m3u
```

这个仓库每天由 GitHub Actions 自动重测刷新，源失效了会自动剔除、能用的新源会自动补上。**车机刷新播放列表就拿到新版。**

### 代理前缀（国内访问 raw 需要）

| 前缀 | 实测速度 | 备注 |
|---|---|---|
| `https://gh-proxy.com/` | 0.3s | **首选** |
| `https://ghproxy.net/` | 1.1s | 备用 |
| `https://ghfast.top/` | 1.6s | 备用 |
| `https://ghproxy.cc/` | 5.9s | 慢，兜底 |
| `https://raw.githubusercontent.com/` | — | 直连，国内常超时 |

> **为什么不用 `github.io`？**
> `https://tommy4x.github.io/iptvlist/car-tv.m3u` 也能用，但 GitHub Pages 在国内稳定性一般，
> 走 `gh-proxy` → `raw` 这条路更快更稳。

## 四、筛选逻辑（为什么可信）

免费源最大的问题是「地址能打开 ≠ 能播」。这个仓库的清单是这么筛出来的：

1. **拉取** 上游源池（iptv-org 公开清单，走 gh-proxy 加速）
2. **实测** 每一条：
   - 拉 m3u8
   - 递归下钻 master / variant playlist
   - 取分片，校验 **MPEG-TS 同步字节 0x47** —— 拿到真 TS 数据才算「能播」
3. **多轮复测取交集**（默认 3 轮）—— 单次通过会混入大量偶发可用的飘源
4. **剔除** 已知不稳定 / 海外 CDN / UDP 组播（车机不支持 UDP，需 udpxy 转 HTTP）

### 踩过的坑（改脚本前先看）

- **分片常用相对路径**：正则只认 `http` 开头会造成大量假阴性，必须 `urljoin(base, uri)` 拼全。
- **并发别贪高**：24 线程同时打国内源会被限流/耗尽连接，表现为「全部假失败」。降到 8 正常。
- **别用整表重测**：515 条全量多轮要 1 小时。改成**快筛（4s 超时零重试）→ 只对幸存者精验**，4 分钟跑完。
- **码率按单分片算**：`单片字节×8÷该片时长`，不能整表字节÷总时长。
- **上游分支别搞错**：`master` = 源定义（`streams/`），`gh-pages` = 成品清单（`countries/`）。
- **dict 顺序反了**：`pool` 是 `{url: name}`，传给只认 `(name, url)` 的函数会全量假失败。

## 七、更新机制

`.github/workflows/refresh.yml` 每天定时（UTC 03:00 / 北京时间 11:00）跑 `refresh.py`，
自动完成「拉源 → 实测 → 筛选 → 提交」全流程。有内容变化才会产生新 commit。

**本地想自己跑一遍：**
```bash
python3 refresh.py --rounds 3 --full
```
